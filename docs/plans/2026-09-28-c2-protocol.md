## 1. The question and the verdicts

Is there one spacer length L such that, in every configuration of section 3, a jump
from rest to L hides **every** hidden-section item without the fold, and collapsing
restores every one, with the detector deciding (G1 + G4)?

- **PASS**: every configuration's band is found and bracketed (section 4); the
  intersection of the conservative bands is at least 32 pt wide; at its midpoint L,
  every 4 pt point of the collar [L-16, L+16] passes one full cycle in every
  configuration; and at L every configuration passes N = 5 full cycles. A full cycle
  (C1's, extended per item): every hidden item (`Target`, `Hidden2..k`) individually
  `hidden(folded: false)` during expansion, fold absent, `.protected` drawn, the
  `Menus` title region unchanged (section 3), no unexplained strip change; then every
  hidden item individually `restored`, reset check passed. A PASS opens stage 2, nothing
  more.
- **PROVISIONAL FAIL** (first non-safety mandatory failure -- the sitting ends there,
  after a clean teardown; no further configuration runs):
  - a configuration has no band after the range expansion of section 4, or
  - the intersection is empty or narrower than 32 pt, or
  - a collar point or a baseline cycle at L fails (not inconclusive).
  C is dropped (and macOS 27 declared read-only) only after a separately authorized
  replication run of that same configuration confirms the failure, or the owner accepts
  the provisional result (feasibility plan 6.2: a failure is replicated once).
- **INCONCLUSIVE** per repeat: preflight never passes, captures unreadable, the frontmost
  or menu-region check fails, or the roster changes before any expansion. Re-run at
  most twice (6.2); a third makes that point *not shown*, which is a failure for a
  mandatory criterion.
- **SAFETY STOP**: terminal, no replication; the runner starts no further
  configuration.

## 2. Environment

- **Isolated account** (feasibility plan section 5): a new standard macOS user created
  by the owner. Its menu bar auto-hide matches the owner's (as the owner states it;
  nothing read from the owner's domains). Screen saver and screen lock off inside that
  account (the owner's action, in that account only). Nothing in the owner's account
  changes; no spacer, helper or event ever touches the owner's bar or preferences.
- **How it runs**: Claude's shell runs as the owner and cannot drive another user's GUI
  session, so the owner starts one self-contained runner in the isolated account and
  leaves; Claude prepares everything and reads the evidence afterwards.
  - Artifacts: `/Users/Shared/IceReverse-c2/apps` (outside `~/Documents`; iCloud xattrs
    break codesign).
  - **Directory ownership**: the owner's account creates `/Users/Shared/IceReverse-c2`
    and its `evidence/` subdirectory (mode 0777, no sticky bit). The runner sets umask 0,
    so every evidence file and directory it creates is readable and deletable from the
    owner's account (deletion is governed by the containing directory, which the owner
    owns). No raw captures anywhere.
  - **Finalization**: each configuration's evidence ends with `manifest.final.json`
    written atomically (temp file + rename) containing every file's SHA-256 and the
    configuration's final status; the runner writes `runner.final.json` the same way
    last. Claude's reader refuses any directory without a final manifest or with a hash
    mismatch; only after a verified copy into `~/IceReverse-evidence/` is the shared copy
    deleted.
  - **Guards** -- the runner refuses to start unless: `id -un` equals the isolated
    account name recorded at build time and differs from the owner's; the display
    matches the recorded geometry (width, height, notch); and the bar's roster, recorded
    before any helper launches, contains only allowlisted items (the MenuBarAgent items
    by bundle id `com.apple.*` and the runner's own helpers). An item not on the
    allowlist refuses the run; a roster change during a configuration is inconclusive
    before any expansion and goes to the latch after it.
  - TCC: Terminal in the isolated account needs Accessibility and Screen Recording; the
    owner grants both once, in that account.
- **Helpers** (vzhelper builds; bundle ids reused so no new menu bar settings entries --
  the Twin/Spacer precedent):
  - `Target` (`com.icespike4.target`) and `Hidden2..4` (`com.icespike4.target`,
    `--role hidden-<n>`, each a distinct VZGlyphs glyph so every hidden item has its own
    unique template);
  - `Spacer` and `Protected` (`com.icespike4.protected`) as in C1;
  - **new role** `Menus` (`com.icespike4.protected`, `--role menus --menu-set
    short|mid|long`): regular activation policy, fixed menu titles, no status item.
  - Placement: C1's sort-key preferred positions (Amendment v9/v10), helper domains only,
    emptied and verified at the end of every configuration. Preflight requires the ordered
    k hidden items to be the only population left of the spacer.
- **Safety contract**: C2 inherits C1's instrument unchanged in every safety respect --
  bounded keyed discovery, the one-miss latch, full-population baseline equivalence at
  teardown, signal precedence (a recorded stop beats INCONCLUSIVE), staged teardown,
  helper dead-man (helpers exit when the controller dies), evidence before exit, the
  time-budget guard, the 20 min watchdog. k-item changes: every hidden item is a latch
  subject after collapse (a hidden item not restored is a latch trip), every hidden item
  is reaped and verified gone at teardown, and the `Menus` helper is quit and verified
  gone last.
- **Process model**: each configuration (and each collar/baseline pass per
  configuration) is its own `vizprobe c2-config` process with its own watchdog, teardown
  and verdict. The runner is a sequencer only; it stops at the first SAFETY STOP or
  PROVISIONAL FAIL. `caffeinate -d -i -w <runner pid>` for the runner's life.

## 3. Configurations

k in {1, 2, 3, 4} hidden-section items (Target plus k-1 extra; spacer and Protected
fixed controls) x three frontmost-menu widths = **12 configurations**.

- **Frontmost menus**: `Menus` is activated before the configuration starts
  (`NSRunningApplication.activate`, no synthetic events). short = last title ends
  <= 400 pt; mid = ends 700-770 pt; long = ends >= 1000 pt (spilling right of the notch).
- **Menu region as a control**: at the configuration's baseline the `Menus` title spans
  (AX, read-only) and their pixels are recorded; every cycle's preflight checks
  `Menus` is frontmost and its spans equal the baseline; the menu region's ink is added
  to the explained spans. A changed or ambiguous menu region makes that repeat
  inconclusive.
- **Long menus and the fold**: the fold must stay independently readable in every
  configuration. A long-menu configuration whose fold is unreadable at baseline (menu
  ink inside the fold region) follows the inconclusive rule of section 1 and, after the
  retries, is *not shown* -- a mandatory C2 failure. G4's safe fallback (shown, never
  reported hidden) is what a product would do there, but it is not evidence of G1, so
  it cannot pass C2. Narrowing C's supported layouts to exclude menus right of the
  notch would need a separate, owner-approved amendment of the feasibility plan (its C2
  row and the mandatory G2(a)); this protocol does not assume one.

## 4. Bracketing, the collar and the length

Per configuration:

1. **Coarse scan** 520-960 pt, 16 pt steps, jump from rest each cycle.
2. **Range expansion** (deterministic): if no hidden step is found, or the lowest or
   highest scanned step is hidden, scan outward in 160 pt chunks (360-504, then
   200-344, ...; 976-1000 upward -- the helper refuses lengths above 1000) as separate
   watchdog-bounded runs, until both edges are found or 0 / 1000 is reached. A band still
   open at 1000 is bracketed by 1000 as its proven top.
3. **Edge refinement** (the plan's "jump path, 4 pt"): the three 4 pt points inside each
   coarse gap that straddles an edge. **Conservative band** = [lowest proven hidden,
   highest proven hidden]; the band is taken as the widest contiguous run, and any
   non-hidden coarse step inside it splits it.

After all 12: intersection of the conservative bands; at least 32 pt wide -> L = its
midpoint rounded to 1 pt; else PROVISIONAL FAIL. Then:

4. **Collar**: every configuration, one full cycle at each 4 pt point of [L-16, L+16]
   (9 points) -- this, not the 16 pt coarse grid, is what proves the margin.
5. **Baseline at L**: every configuration, N = 5 full cycles.

Pure logic (band extraction, splitting, expansion chunks, refinement points,
intersection, L, collar points, accounting) lives in a new standard-library-only target
`C2Core`, 100 % line coverage.

## 5. Time budget

About 28.5 s per cycle (C1: 731 s for 24 cycles plus setup). Per configuration: 28
coarse + 6 refinement = 34 cycles, about 17 min, inside the 20 min watchdog; range
expansion adds separate runs only when needed. **Sitting A** (brackets): 12 x 17 min
= about 3.4 h. **Sitting B** (collar + baseline): 12 x (9 + 5) = 168 cycles = about
1.4 h, one process per configuration per pass. Early stop can make either shorter.

### 6.1 T3 design (C1's instrument generalized, not forked)

C1's stage is parameterized rather than copied, so every C1 safety fix stays in one
place; `vizprobe c1` keeps k = 1, no `Menus`, C1's own lengths, and its behaviour and
tests unchanged.

1. **C1Core**: `PreflightOrderCheck` takes the ordered hidden ids (`[target, hidden-2,
   ...]` must be the first k items, then the spacer); `PlacementPlan` plans k hidden
   items left of the spacer at the real pitch, sort keys `floor + (k + 2 - i) * step`
   (leftmost highest); `PlacementGate` requires hidden_1 < ... < hidden_k < spacer <
   Protected < every other on-bar item. The C1 signatures remain as k = 1 wrappers.
2. **C1Live**: `C1Discoverer` takes the hidden keys instead of one target key.
3. **C1Stage**: `targetKey` becomes `hiddenKeys` (Target first); launch order Protected,
   spacer, then hidden_k ... hidden_1 (each lands leftmost); the verification's section
   map holds all k; a cycle's reading is `hidden(folded: false)` only when every hidden
   key reads so, `stillDrawn` when all are drawn, and `notShown` for any mix or refusal;
   `restored` requires every hidden key back; reap/PID sets include every helper.
   A run profile carries k, the optional `Menus` helper, and the length plan: C1's
   (scan + smoke) or an explicit list (C2's coarse / expansion / refinement / collar /
   baseline), each length one full cycle with 6.2's retries (`C2Retry`).
4. **Menus: controlled, not observed.** The `Menus` helper launches first in step 2,
   is calibrated with `menus <n>` against its AX title spans (`C2MenuWidth.adjust`, at
   most 40 steps, else the configuration is INCONCLUSIVE), and activated; every
   preflight checks it is still frontmost with the calibrated spans (a new environment
   seam), else the repeat is inconclusive. Its titles are **not** added to the observed
   population: the frozen `StripAssessor` bounds the fold region by the leftmost observed
   item (`foldRegion(upTo:)`), so a menu title there would collapse that region and turn
   an unreadable fold into a false `absent` (found while implementing; the earlier
   "menus as observed items" idea is withdrawn). Consequence (INFERRED, to be measured):
   with menus right of the notch their ink sits in the fold region, the fold reads
   unreadable at baseline, and under section 3 each long-menu configuration is *not
   shown* -- a PROVISIONAL FAIL. **Sitting A therefore runs the three long-menu
   configurations first**, so this likely outcome is known within minutes.
5. **vizprobe `c2-config`** (one configuration, one length list, one watchdog) and
   **`c2-run`** (the sequencer: spawns `c2-config` processes, reads their final
   manifests, asks `C2Core` for the next list -- expansion, refinement -- and applies the
   stop rules). `run-c2.sh` only checks the account and starts `c2-run`.
